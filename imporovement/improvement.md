## 1. 并行化与工程优化

这一部分最直接，目标不是改方法，而是在尽量不改变实验语义的前提下，提高训练和评估速度，减少重复计算。当前项目里很多地方都存在同一种通病：单样本、单 step、单次前向地串行执行，本来可以合并、缓存或向量化。

我认为这里最重要的两个方向是：

### 1.1 向量化

当前代码里有不少逻辑本质上还是“for 循环包住模型调用”，这会让 GPU 吞吐很低。

优先可以考虑的点：

- `evaluate.py` 中多处 `generate` / `answer_probabilities` / `complete` 都是单条样本调用，已有 TODO 提到 batch 化。这一部分如果做成 batch 推理，通常会显著提速。
- `generate_dataset_cots` 目前逐条生成 CoT、逐条算 answer probability，属于明显的串行路径。
- `data.py` 中 `qcot_encoder` 和 POS 对齐逻辑目前偏单条样本处理，未来可以改成“先批量 tokenizer，再批量构造 label mask”，至少在 `pos_filter=False` 的主路径上应当先向量化。
- `segment.py` 里对齐过程目前也还是逐条做，可以考虑改成多条并行预处理。
- 训练与评估里，很多位置实际上是在做“同一操作重复作用到不同样本”，例如 answer letter 概率计算、固定 prompt 下的生成、step probability 计算，这些都适合统一 pad 后批量前向。

需要注意的现实问题：

- 不同 instance 的 CoT 长度不同，需要 padding。
- 不同任务的选项数量不同，`A/B/C/D/E` 的读取要分组处理，或者统一按最大选项数处理后再 mask。
- 某些 `generate` 路径比 teacher-forcing 更难 batch 化，但依然值得做，至少可以把同类 prompt 放进一个 batch。

总体判断是：这个项目目前不是算子本身慢，而是大量 GPU 时间被低吞吐、小 batch、串行 Python 控制流浪费掉了。

### 1.2 缓存

第二个大头是缓存。当前实现里有许多在实验过程中根本不会变化的量，却被重复计算。

典型例子：

- `oracle_model` 是冻结的，而在默认 `stepwise=True` 的设置下，`forget_inputs` 也是固定的，因此 `forget_loss_oracle` 可以在进入 epoch 循环前缓存，而不是每个 step / epoch 都重新前向。
- 如果 retain 样本不变，那么 `npo_KL` 里的 `retain_outputs.logits` 也可以缓存，至少 oracle 侧可以缓存。
- `qcot_encoder` 输出的 `input_ids / labels / attention_mask` 都可以预编码，不应该在 `__getitem__` 里每次重做 tokenizer 和 label 构造。
- `num_targets()` 目前会再次触发 `__getitem__`，这相当于训练前先把数据管线又完整跑一遍；如果改成预先保存长度信息，就不需要重复执行。
- 数据集构造时，一些 `prefix` 拼接、prompt 拼接、bookkeeping 字段也都可以预先展平。

从更高层看，缓存可以分三层：

1. 模型层缓存：冻结参考模型的 loss、logits、log-probs。
2. 数据层缓存：tokenization、mask、prefix 拼接、POS 对齐结果。
3. 评估层缓存：固定样本上的 prompt、answer token 索引、固定 CoT 的编码结果。

### 1.3 当前 TODO 之外，仍然存在的共性问题

虽然代码里已经写了一些 TODO，但并不是只有被标出来的地方才有问题。更普遍的症状包括：

- 单样本前向太多，尤其是 `generate` 路径。
- 训练和评估对同一个样本反复做相同编码。
- `oracle_model` 前向重复且未缓存。
- 数据集接口把大量预处理放在 `__getitem__`，导致 DataLoader 每次取样都做重复工作。
- 实验粒度是“每个 step 一个独立训练过程”，导致模型加载、数据准备、评估都被放大了很多次。

因此，第一部分的一个更系统的结论是：

> 这里最值得优先做的不是盲目并行，而是先把“重复且确定不变”的部分缓存掉，再把“本质同构的重复模型调用”改成 batch/向量化。

## 2. faithfulness 测量与目标函数本身的疑问

这一部分比工程优化更重要，因为它关系到这个项目究竟测到了什么。

### 2.1 当前方法更像“分布偏好重写”，不等于真实遗忘

我目前的一个核心观点是：这个项目的训练目标更像是在改变模型的输出分布偏好，而不是确保模型真的遗忘了相关知识或推理机制。

更具体地说，当前做法是：

- 选定某一个 CoT step。
- 在给定 prompt 和 prefix 的条件下，压低该 step 的生成概率。
- 然后观察最终答案是否改变。

这说明它在行为层面做了一次干预，但未必能说明内部知识真的被删除了。

我比较担心的一种 failure mode 是：

- 模型内部表征和真实求解路径并没有本质变化。
- 只是某一层附近的输出分布被重写了，导致该 step 不再容易以原有表述被生成。
- 于是模型看起来“忘掉了这一步”，但实际上只是学会了不这样说，或者换一种说法说，甚至内部仍然沿着近似同样的推理路径完成决策。

如果是这样，那么该方法更像是在测：

> 当一段显式自然语言 reasoning 被压制后，最终行为会不会变化？

而不是在测：

> 模型是否真的从内部遗忘了与该 step 对应的知识或因果推理路径？

因此，当前方法更适合作为一种 **behavioral faithfulness probe**，而不应被直接等同为 **mechanistic knowledge unlearning**。

### 2.2 “答案不变”与“step 不重要”之间并不能直接画等号

在当前设定下，如果某一步被压低后答案仍然不变，可能有至少三种解释：

- 这一步确实不是因果关键步骤。
- 干预只改了表面表达，没有改到底层求解机制。
- 模型只是换了一种等价说法或等价内部路径。

所以：

- 答案变化，是比较强的证据，说明这一步可能与最终行为有因果关系。
- 答案不变，则是比较弱的证据，不能直接推出“该 step 不重要”。

这意味着项目当前的结论解释需要更谨慎，不能把“未引起答案翻转”直接解释成“推理不 faithful”或“step 不起作用”。

### 2.3 当前损失函数也可能放大这种问题

当前训练目标主要是在 token-level 上压低某个 step 的 likelihood，同时用 retain 项防止模型整体塌陷。这种目标有几个潜在问题：

- 它直接作用的是可见文本序列的生成概率，而不是内部机制。
- 它可能鼓励模型回避某个固定表述，而不是回避该表述背后的知识或逻辑关系。
- 如果只压原始 step，而不压 paraphrase、近义改写或逻辑等价说法，那么模型完全可能学会“换个说法继续表达同样内容”。
- `npo_KL` 中 retain 的 KL 约束目前是整段分布匹配，但 forget 部分仍然主要是 sequence likelihood 压制，这种目标天然更偏向输出层行为调整。

换句话说，当前损失函数更像是：

> 让模型远离这条目标文本。

而不是：

> 让模型远离这类知识、这类推理模式、或这条因果链。

同时，retain项的选择会使得优化可能存在不稳定的情况

- 如果用类似grpo的组群或对比优化办法呢？

### 2.4 如果目标是真正更强的“遗忘”，可能需要更接近预训练或对比学习的形式

如果希望模型不只是“别这么说”，而是更接近“真的忘掉了这条知识或推理支撑”，我认为可以考虑比当前 NPO 更强的目标设计。

一个方向是更接近预训练式或表征式约束：

- 不只在单条 CoT step 上做序列概率压制。
- 而是在一簇相关问题、相关 paraphrase、相关推理模板上共同压制同一知识。
- 同时检查答案、隐藏状态、或 probe 可读性是否都发生变化。

另一个方向是对比学习式设计：

- 将目标 step 及其 paraphrase 视为负样本。
- 将不依赖该知识的替代推理、合理拒答、或中性改写视为正样本。
- 在表示空间或分布空间中，显式拉远负样本、拉近正样本。

这里的关键不是“把正确 step 当成一个负样本”这么简单，而是要避免只学到字符串级规避。因此更合理的设计应当至少包含：

- 原始 step
- 该 step 的多种改写/paraphrase
- 逻辑等价表达
- 替代性合理推理或拒答形式

否则模型还是可能只学会对某一个表面形式做 suppression。

### 2.5 一个更稳妥的判断

基于以上分析，我倾向于这样描述该项目的定位：

- 作为 CoT faithfulness 的行为探针，这个项目是有价值的。
- 作为“知识真正被遗忘”的证据，这个项目目前远远不够。
- 如果后续要扩展成更强的 unlearning 方法，应当同时加入：
  - paraphrase-level 干预，
  - answer-level 干预，
  - representation-level 诊断或约束。

简化地说：

> 当前方法回答的是“删掉一句 reasoning 之后，行为会不会变”；
> 但它还没有回答“模型脑中对应的知识、路径或因果结构是否真的被删除”。

## 4. `non-stepwise` 路径当前存在语义错位，应该视为实现问题

除了上面的工程优化与方法论问题，当前实现里还有一个更具体的缺陷：`stepwise=False` 时，训练逻辑与评估/logging 逻辑并没有严格对齐。

### 4.1 当前 `non-stepwise` 实际训练了什么

需要区分两种情况：

- `strategy='sentencize'` 且 `stepwise=False` 时，dataset 会包含该 target CoT 的所有 step。也就是说，同一个模型会在一次训练过程中，依次对整条链的多个 step 做联合压低。
- `strategy='full'` 且 `stepwise=False` 时，训练对象是整条 CoT 作为一个 completion，被一次性压低。

所以 `non-stepwise` 并不是“没有做 CoT unlearning”，而是：

- 要么在同一个模型里联合压低整条链的多个 step；
- 要么直接压低整条完整 CoT。

### 4.2 评估与日志当前仍然沿用了 stepwise 的解释方式

问题在于，主循环在 `stepwise=False` 时只会执行一次 `unlearn_single(..., step_idx=0, ...)`，而 `evaluate()` 里仍然会：

- 用 `target['segmented_cot'][step_idx]` 作为“被遗忘的 target step”；
- 用第 0 步构造 `target_cot_step_prefix`；
- 在日志里继续沿用单步遗忘的记录方式。

这会导致一个语义错位：

- 训练时，模型可能已经对整条链的多个 step 做了联合干预；
- 但评估输出和日志字段却仍然把“第 0 步”当作当前 target 来解释。

因此在 `non-stepwise` 设置下，现有结果文件中的：

- `target_cot_step`
- `target_cot_step_prefix`
- `step_idx`

都不能再被直接理解为“真实训练目标”，至少对 `sentencize + non-stepwise` 这条路径是不准确的。

### 4.3 这不只是展示问题，还会影响实验解释

这个问题的严重性在于，它不只是日志写得不够清楚，而是会直接影响对实验结果的解读。

例如：

- 如果 `non-stepwise` 下答案发生变化，不能再像 stepwise 那样解释成“某一个 step 被删掉后触发了答案变化”。
- 如果 `non-stepwise` 下第 0 步概率变化很大，也不能说明模型主要遗忘的是第 0 步，因为训练时可能已经对整条链其他 step 都施加了约束。

换句话说，`stepwise=False` 下当前输出格式会把“整链联合干预”的结果误写成“单步干预”的结果。

### 4.4 这部分应当如何修复

我认为这一项应该明确列为实现 bug 或至少是实验语义缺陷，后续需要单独修正。比较合理的改法包括：

- 如果训练是 `sentencize + non-stepwise`，那么评估时就不应继续用单个 `step_idx` 来代表目标，而应明确记录“联合遗忘了哪些 step”。
- 如果训练对象是 `full-chain`，那么日志里就不应该再保留 `target_cot_step` 这一类字段，而应改成 `target_cot` 或 `target_chain`。
- `evaluate()` 需要根据 `stepwise` 和 `strategy` 分支，分别定义“当前训练目标是什么”，不能复用 stepwise 语义。
- 结果文件命名与字段设计也应当区分：
  - 单步遗忘；
  - 多步联合遗忘；
  - 整链遗忘。

简化地说：

> 当前 `non-stepwise` 路径并非没有训练 CoT，
> 而是训练语义已经变了，但评估和日志仍按 stepwise 方式解释，
> 这会导致结果被误读，因此应当在后续改进中作为单独问题修复。
